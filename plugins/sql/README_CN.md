# 插件：sql

[English](README.md) · 简体中文

将 **SQL 迁移**读成图中的事实：一棵树声明它所维护的模式——表、列、视图、
用户自定义类型与索引，以及它们之间的引用。manifest 为 `sql@1`，声明
**`.sql`**。纯 Rust（`sqlparser`），因此沙箱既不需要 wasi-sdk，也不需要 C
工具链。

每个代码插件最多只能在字符串字面量里看见一个表名，仅此而已。它们都不读那份说明
这个表**是什么**的 DDL——它有哪些列、列是什么类型、哪些列指向另一张表。那些内容
一直待在一个没有任何解析器声明的迁移目录里。

## 是序列，而不是集合

这是一个 SQL 插件必须做对的一件事，也是本插件直接实现契约的两个阶段、而不采用
`Simple` 外观的原因。

迁移是一个**序列**。`0001_create_users.sql` 添加的列，会被 `0014_trim.sql`
删掉。逐个文件解析再取并集的解析器，报告出的是一个在任何时刻都不曾存在过的
模式：曾经添加过的列全都在，而所有的删除一个都没生效。

所以 `parse` 分块并行地做昂贵的那一半——词法、语法，并把每条语句归约为它所做的
变更——而 `assemble` 按迁移顺序**重放**这些变更，只发出最后一次迁移留下的那个
模式。顺序是在那里依据路径重新算出来的，因为契约要求插件的结果不得依赖于分块
边界落在何处。

三个值得知道的推论：

- **数字串按数值比较。** 按字典序 `10_x.sql` 排在 `9_x.sql` 之前，于是一棵没有
  补零编号的树，会在看起来排序得完美无缺的同时，以错误的顺序重放。
- **反向迁移不被读取**，否则刚读进来的树会被它撤销。可识别四种约定：
  `*.down.sql`（golang-migrate、dbmate）、`down.sql`（Diesel）、Flyway 的
  `U1__*.sql` 撤销脚本，以及文件内的 `-- +goose Down` / `-- +migrate Down`
  指令——对后者只取文件中正向的那一半。
- **`DROP` 一个本树中没有任何迁移创建过的对象，只被计数，不被执行。** 它指的是
  这棵树之外的对象，因此一个零散的清理 fixture 无法清空整个模式。报告会说明是
  哪些。

## 方言

显式声明，绝不嗅探——从文件内容去猜方言，正是这个家族所拒绝的那类猜测；而所支持
的三种方言在足够多的语法上互不相同，以至于一次错误的猜测会变成一个被归因于该文件
的解析错误。

```toml
[plugins.sql]
dialect = "postgres"   # 或 "mysql"、"sqlite"
```

不设置时，通用方言接受最宽的语法，足以应付多数树。读不了的文件会被计数并指名，
报告中还会带上那条提示：指明方言才是能改变结果的那一个设置。需要设置它的常见
原因是 MySQL 的反引号引用与 `AFTER <column>` 列位置语法。

## 节点与边

| 节点 | 键 | 示例 |
|---|---|---|
| `Table` | 书写时的限定名 | `users`、`public.users` |
| `Column` | 所属表的键加上自己的名字 | `users.email` |
| `View` | 书写时的限定名 | `active_authors` |
| `Type` | 书写时的限定名 | `user_role` |
| `Index` | 书写时的限定名 | `idx_users_email` |
| `Migration` | 文件路径 | `migrations/0001_users.sql` |

| 边 | 从 → 到 | 含义 |
|---|---|---|
| `HAS_FIELD` | `Table`/`View`/`Type` → `Column` | 一个列，或复合类型的一个字段 |
| `IS_TYPE` | `Column` → `Type` | 该列所写的类型是本树声明过的类型 |
| `REFERENCES` | `Column` → `Column`/`Table` | 一个外键 |
| `INDEXES` | `Index` → `Table`、`Index` → `Column` | 索引覆盖了什么 |
| `SELECTS_FROM` | `View` → `Table`/`View` | 定义查询读取的一个关系 |
| `DEFINES` | `Migration` → 任何对象 | 是哪次迁移创建了它 |

**只有 DDL 写了 schema，键里才有 schema。** 补一个默认值——Postgres 补
`public`、MySQL 补数据库名、SQLite 补 `main`——等于发明一个键，而且每种方言发明
出来的都不一样。当恰好只有一个对象可能匹配时，未限定名会解析到已限定的那个；
出现两个候选就是歧义，歧义被报告，而不被猜测。

**内置类型不产生节点。** 为 `text` 建一个 `Type` 节点，会出现在每一个模式里、
不携带任何信息，并把一棵树真正声明的那些类型埋掉。书写的类型作为属性挂在列上，
而 `IS_TYPE` 只指向某次迁移声明过的类型——匹配时会越过类型修饰符与数组标记，
因此 `user_role[]` 与 `varchar(40)` 都能正确解析。

**只要两端能够配对，外键就是列到列的。** `REFERENCES workspaces (id)` 写明了
两端。`REFERENCES workspaces` 只写了表，而 SQL 规定这指的是被引用表的主键——
重放后的模式本就持有它，所以这里是解析出来的，而不是退化成粗粒度。每条边都在
`_resolved_by` 里说明自己属于哪种情况：`foreign-key`、
`foreign-key-primary-key`，或者当复合主键与引用列对不上时的
`foreign-key-table`。

**绝不写出一条端点没有任何节点声明的边。** 指向另一个数据库中某张表的引用，或者
建在后续迁移已删除的表上的索引，都会被跳过——在这个图里，一个悬空的边端点会让
**整次**写入失败，而不只是这一条边。

**未命名的索引只被计数，不被定键。** `CREATE INDEX ON users (email)` 把名字留给
方言决定，而发明一个名字等于把节点定键在没有任何迁移写过的东西上。它的列本来就
已经在表上了。

## 它不做什么

**它不读代码中内嵌的 SQL**，因此不会写出从函数到表的边。那需要外层函数的键，而
只有那门语言自己的插件知道这个键；并且一条端点没有节点声明的边会让整次写入失败，
而不只是这一条边。诚实的路线是 `wire` 为 HTTP 路由已经采取的那一条——两侧各自
写出事实，由一个动词在查询时做匹配——那是另一项独立的工作。

同样不读：存储过程与触发器；行级安全策略；`GRANT`；作为独立对象的序列；以及
PL/pgSQL 匿名块（`DO $$ … $$`）——sqlparser 不解析它，那些文件会被计数并指名。

## 实测

在设定了方言的前提下，针对真实的迁移树：

| 树 | 文件 | 跳过 | 表 | 列 | 类型 | 索引 |
|---|---:|---:|---:|---:|---:|---:|
| Yaak（`yaak-models`，sqlite） | 71 | 0 | 21 | 284 | 0 | 3 |
| 某个 Postgres 服务 | 44 | 0 | 15 | 107 | 0 | 20 |
| 另一个 Postgres 服务 | 20 | 1 | 23 | 202 | 8 | 20 |

唯一那次跳过是一个 `DO $$ … $$` 块。Yaak 的 23 条外键全部写成不带列的
`REFERENCES <table>`，并且 23 条全部解析到了主键。

## 构建与测试

```sh
just sql-plugin          # 构建到 wasm32-wasip2
cd plugins/sql && cargo test
```

测试在本机运行：一切都走真实流程——lower、replay、emit——只把 `host::read`
排除在外，因此文件以文本形式给出。
