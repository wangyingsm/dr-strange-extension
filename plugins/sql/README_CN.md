# 插件：sql

[English](README.md) · 简体中文

将 **SQL 迁移**读成图中的事实：一棵树声明它所维护的模式——表、列、视图、
用户自定义类型与索引，以及它们之间的引用——随后再对照这份模式，读出**写在代码里
的查询**。manifest 为 `sql@1`，声明 **`.sql`**。纯 Rust（`sqlparser`），因此沙箱
既不需要 wasi-sdk，也不需要 C 工具链。

每个代码插件最多只能在字符串字面量里看见一个表名，仅此而已。它们都不读那份说明
这个表**是什么**的 DDL——它有哪些列、列是什么类型、哪些列指向另一张表。那些内容
一直待在一个没有任何解析器声明的迁移目录里。而一旦手里有了 DDL，字面量里的一条
语句就不再只是一个字符串，而成为关于那些表的事实。

## 是序列，而不是集合

这是一个 SQL 插件必须做对的一件事，也是本插件直接实现契约的两个阶段、而不采用
`Simple` 外观的原因。

迁移是一个**序列**。`0001_create_users.sql` 添加的列，会被 `0014_trim.sql`
删掉。逐个文件解析再取并集的解析器，报告出的是一个在任何时刻都不曾存在过的
模式：曾经添加过的列全都在，而所有的删除一个都没生效。

所以 `parse` 分块并行地做昂贵的那一半——词法、语法，并把每条语句归约为它所做的
变更——而 `assemble` 按迁移顺序**重放**这些变更，只发出最后一次迁移留下的那个
模式。顺序是在那里依据路径重新算出来的，因为契约要求插件的结果不得依赖于分块
边界落在何处。

三个值得知道的推论：

- **数字串按数值比较。** 按字典序 `10_x.sql` 排在 `9_x.sql` 之前，于是一棵没有
  补零编号的树，会在看起来排序得完美无缺的同时，以错误的顺序重放。
- **反向迁移不被读取**，否则刚读进来的树会被它撤销。可识别四种约定：
  `*.down.sql`（golang-migrate、dbmate）、`down.sql`（Diesel）、Flyway 的
  `U1__*.sql` 撤销脚本，以及文件内的 `-- +goose Down` / `-- +migrate Down`
  指令——对后者只取文件中正向的那一半。
- **`DROP` 一个本树中没有任何迁移创建过的对象，只被计数，不被执行。** 它指的是
  这棵树之外的对象，因此一个零散的清理 fixture 无法清空整个模式。报告会说明是
  哪些。

## 方言

显式声明，绝不嗅探——从文件内容去猜方言，正是这个家族所拒绝的那类猜测；而所支持
的三种方言在足够多的语法上互不相同，以至于一次错误的猜测会变成一个被归因于该文件
的解析错误。

```toml
[plugins.sql]
dialect = "postgres"   # 或 "mysql"、"sqlite"
```

不设置时，通用方言接受最宽的语法，足以应付多数树。读不了的文件会被计数并指名，
报告中还会带上那条提示：指明方言才是能改变结果的那一个设置。需要设置它的常见
原因是 MySQL 的反引号引用与 `AFTER <column>` 列位置语法。

## 节点与边

| 节点 | 键 | 示例 |
|---|---|---|
| `Table` | 书写时的限定名 | `users`、`public.users` |
| `Column` | 所属表的键加上自己的名字 | `users.email` |
| `View` | 书写时的限定名 | `active_authors` |
| `Type` | 书写时的限定名 | `user_role` |
| `Index` | 书写时的限定名 | `idx_users_email` |
| `Migration` | 文件路径 | `migrations/0001_users.sql` |
| `Statement` | 字面量被书写的位置 | `src/db.rs:114` |

| 边 | 从 → 到 | 含义 |
|---|---|---|
| `HAS_FIELD` | `Table`/`View`/`Type` → `Column` | 一个列，或复合类型的一个字段 |
| `IS_TYPE` | `Column` → `Type` | 该列所写的类型是本树声明过的类型 |
| `REFERENCES` | `Column` → `Column`/`Table` | 一个外键 |
| `INDEXES` | `Index` → `Table`、`Index` → `Column` | 索引覆盖了什么 |
| `SELECTS_FROM` | `View` → `Table`/`View` | 定义查询读取的一个关系 |
| `READS` | `Statement` → `Table`/`View` | 代码中的查询读取的一个关系 |
| `WRITES` | `Statement` → `Table` | 代码中的查询写入的目标 |
| `USES_COLUMN` | `Statement` → `Column` | 查询所命名的列，边上带 `role` |
| `DEFINES` | `Migration` → 任何对象 | 是哪次迁移创建了它 |

`READS`、`WRITES` 与 `USES_COLUMN` 刻意沿用 [`xml`](../xml) 插件为 MyBatis
mapper 已经写出的那套词汇：Rust 里的一条查询与 mapper 中的一个 `<select>`，是
关于同一张表的同一类事实，而无论 SQL 写在哪里，"谁动了这张表"都应当由同一条查询
回答。

## 写在代码里的查询

字符串字面量里的一条语句，会被对照迁移所声明的模式读出，并成为一个以书写位置为键
的 `Statement` 节点。读两者用的是同一套语法，因此一条查询要么被理解，要么被拒绝
——绝不半猜。

```
$ drsg context agents
agents  Table
primary_key: row_id
READS ← (2):
  crates/ip-storage/src/postgres/agent.rs:64   Statement  …/agent.rs:64-66
  crates/ip-storage/src/postgres/agent.rs:174  Statement  …/agent.rs:174-175
WRITES ← (13):
  crates/ip-storage/src/postgres/agent.rs:94   Statement  …/agent.rs:94
  …
```

可读出八种语言的字面量：Rust（含 `r#"…"#`）、Go、Python、TypeScript 与
JavaScript、Java、Kotlin、C#（含 `@"…"`）以及 C。注释是被跳过的，而不只是被忽略
——在 `'` 用于引字符串的语言里，一条注释中的撇号会打开一个字面量，并在下一条注释
的撇号处闭合，把中间的一切吞掉。语言会拼接的字面量也会被拼接：Java、C#、Go、
TypeScript 与 Python 的 `+`，以及 C 和 Python 的相邻拼接。

**不写出指向外层函数的那条边。** 那需要函数的键，而只有那门语言自己的插件才能铸
出它；并且一条端点没有节点声明的边会让**整次**写入失败。图中持有的是跨度：一个
`Statement` 与每个定义节点一样携带 `file`、`line` 与 `end_line`，因此哪个函数包住
了它，是对图中既有事实的算术。今天这需要两条查询，因为 openCypher 子集每个
`MATCH` 只持有一条线性路径，而这个连接是两者的笛卡尔积：

```text
MATCH (s:Statement) WHERE s.file = '<path>' RETURN s.line, s.sql
MATCH (f:Function)  WHERE f.file = '<path>' RETURN f.name, f.line, f.end_line
```

**一个洞被读作绑定参数。** `${…}`、`#{…}`、`{…}`、`$name` 与 `%s` 绝大多数时候
都站在取值的位置上，而看见这个洞的语法会拒绝整条语句——偏偏那正是读者最想读到的
那条查询。把它换成 `?`，读到的就是驱动将要看到的文本，节点上会标 `parameterized`。
如果那个洞原本站在标识符的位置，`FROM ?` 就不是一条语句，解析随之失败：这是诚实
的结果，因为一张在运行时才被命名的表，并不是关于这棵树的事实。SQL 字符串字面量
里的洞不会被动，于是 `'{"a":1}'` 依旧是那份 JSON。

**被拒绝的查询会用通用 SQL 重试一次。** 所声明的方言是为迁移服务的，在那里猜错
语法会改变模式；而查询是另一种风险——更宽松的语法最多只能多添一条语句，而它的表名
来自它自己的文本。并且一个仓库里常常两者俱存：一个 Postgres 主库与一个 SQLite
缓存，`$1` 与 `?` 两种占位符写在相邻的模块里。在一棵真实的树上，只声明
`postgres` 读出了 254 条中的 115 条；加上重试则读出 197 条。凡是由回退读出的，
节点会标 `_resolved_by: generic-grammar`。

**列上的边会带上它被命名时所处的角色** —— `projection` 表示调用方拿回的东西
（`SELECT` 列表或 `RETURNING`），`assignment` 表示 `UPDATE … SET` 或 `INSERT` 的
列清单，`reference` 表示其余一切。一个列若出现在两种角色里，按上述顺序保留第一种。

**不关于任何表的语句不成为节点。** `SELECT 1`，或者 `FROM
generate_series(1, 10)`：为它建一个节点，只会携带一个字面量而不带一条事实。表值
函数所站的位置与表完全相同，但两者会被分辨开，因此它不铸出任何东西。

**以 SQL 自己的词开头的字符串，还不算候选。** 用户界面里满是 `Delete` 按钮与
`Select a workspace` 占位符；在一棵真实的树上，仅凭开头那个词就把其中 178 个送进
了解析器，而一份指名 178 个从来不是查询的字符串的报告，什么也解释不了。一条关于
表的语句总会用 `FROM`、`INTO` 或 `SET` 命名那张表，这就是这道闸门的后半截。

源文件是通过 host 拉取的，而不是路由到这里的：路由器把每个文件交给恰好一个
handler，而 `.rs` 属于 rust 插件那一桶，所以索取是唯一的办法——而这正是那份授权的
用意。这次扫描是串行的，在 `assemble` 里，因为 host 每次 `parse` 调用只交给本插件
一个 `.sql` 文件，而解析一个表名需要重放后的模式。设 `inline = false` 可只读迁移；
超过 1 MiB 的文件会被计数并指名，而不会被词法分析。

**只有 DDL 写了 schema，键里才有 schema。** 补一个默认值——Postgres 补
`public`、MySQL 补数据库名、SQLite 补 `main`——等于发明一个键，而且每种方言发明
出来的都不一样。当恰好只有一个对象可能匹配时，未限定名会解析到已限定的那个；
出现两个候选就是歧义，歧义被报告，而不被猜测。

**内置类型不产生节点。** 为 `text` 建一个 `Type` 节点，会出现在每一个模式里、
不携带任何信息，并把一棵树真正声明的那些类型埋掉。书写的类型作为属性挂在列上，
而 `IS_TYPE` 只指向某次迁移声明过的类型——匹配时会越过类型修饰符与数组标记，
因此 `user_role[]` 与 `varchar(40)` 都能正确解析。

**只要两端能够配对，外键就是列到列的。** `REFERENCES workspaces (id)` 写明了
两端。`REFERENCES workspaces` 只写了表，而 SQL 规定这指的是被引用表的主键——
重放后的模式本就持有它，所以这里是解析出来的，而不是退化成粗粒度。每条边都在
`_resolved_by` 里说明自己属于哪种情况：`foreign-key`、
`foreign-key-primary-key`，或者当复合主键与引用列对不上时的
`foreign-key-table`。

**绝不写出一条端点没有任何节点声明的边。** 指向另一个数据库中某张表的引用，或者
建在后续迁移已删除的表上的索引，都会被跳过——在这个图里，一个悬空的边端点会让
**整次**写入失败，而不只是这一条边。

**未命名的索引只被计数，不被定键。** `CREATE INDEX ON users (email)` 把名字留给
方言决定，而发明一个名字等于把节点定键在没有任何迁移写过的东西上。它的列本来就
已经在表上了。

## 它不做什么

**它不写出从函数到语句的边**——原因，以及图中改为持有的那个跨度，见上面的
*写在代码里的查询*。

**它不读在运行时拼装出来的查询。** 由分支拼出的语句，或通过一个洞来命名自己那张表
的语句，都会被计数并指名，而不被猜测。它也不跟进查询构建器：Diesel 的
`users.filter(…)` 或 sqlx 的宏，是用一门语言自己的类型声明同一件事，读它们是那门
语言插件的工作。

同样不读：存储过程与触发器；行级安全策略；`GRANT`；作为独立对象的序列；以及
PL/pgSQL 匿名块（`DO $$ … $$`）——sqlparser 不解析它，那些文件会被计数并指名。

## 实测

在设定了方言的前提下，针对真实的迁移树：

针对真实的树，且已设定方言。*跳过*指无法解析的迁移文件；*拒绝*指开头像查询、却
无法解析的字面量。

| 树 | 迁移 | 跳过 | 表 | 列 | 读取源文件 | 语句 | 拒绝 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 某个 Postgres 服务 | 46 | 0 | 16 | 107 | 210 | 197 | 12 |
| 另一个 Postgres 服务 | 22 | 1 | 23 | 202 | 87 | 130 | 3 |
| Yaak（sqlite） | 68 | 0 | 23 | 284 | 1024 | 20 | 2 |
| 某个 MySQL 服务 | 3 | 0 | 2 | 12 | 219 | 22 | 7 |

唯一那次迁移跳过是一个 `DO $$ … $$` 块。Yaak 的 23 条外键全部写成不带列的
`REFERENCES <table>`，并且 23 条全部解析到了主键。第一棵树正是只声明 `postgres`
读出 115 条、而通用语法重试读出 197 条的那一棵：它把一个 Postgres 主库和一个
SQLite 缓存并排放着。对其中最大的一棵做整树 digest，连同其余所有插件，耗时不到
三秒。

## 构建与测试

```sh
just sql-plugin          # 构建到 wasm32-wasip2
cd plugins/sql && cargo test
```

测试在本机运行：一切都走真实流程——lower、replay、扫描、emit——只把 `host::list`
与 `host::read` 排除在外，因此文件以文本形式给出。
